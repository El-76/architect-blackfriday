## Задание 7: Проектирование схем коллекций для шардирования данных

### Orders (заказы)

#### Структура данных

Коллекция orders включает заказы клиентов и содержит атрибуты:

* Уникальный идентификатор заказа
* Идентификатор клиента
* Дату и время оформления заказа
* Список заказанных товаров и их цену
* Статус заказа
* Общую сумму заказа
* Геозону заказа

```
{
    "_id": "66b5c3e29f8a7d1b3e4f5a6b",
    "user_id": 1822833,
    "created_at": "2026-07-15 15:34:22",
    "items": [
        {
            "product_id": "77b5c3e29f8a7d1b3e4f5a6b",
            "price": 1233.22,
            "quantity": 1
        },
        {
            "product_id": "88b5c3e29f8a7d1b3e4f5a6b",
            "price": 876.23,
            "quantity": 1
        }
    ],
    "status": "created",
    "total_amount": "2109.45",
    "geo": "RU"
}
```

Например, заказ пользователя из Москвы может включать товары из категорий «Электроника» и «Книги».

Добавлено количество товаров.

#### Основные операции

* Быстрое создание заказов с одновременным списанием остатков.
* Поиск истории заказов конкретного пользователя.
* Отображение статуса заказа.

### Products (товары)

Коллекция products хранит сведения о товарах и включает такие атрибуты:

* Уникальный идентификатор товара
* Наименование
* Категорию товара
* Цену
* Остаток товара в каждой геозоне
* Дополнительные атрибуты (цвет, размер)

Например, в Екатеринбурге есть в наличии 50 штук товара «Смартфон X», а в Калининграде — 30.

В каждом датацентре храним свою копию списка товаров с остатками в локальном датацентре, см. ниже мотивацию в секции Стратегии и ключи шардирования, предполагаем что обновление остатков будет происходить локально, а добавление товара - не такая частая операция и требует лишь eventual consistency.

```
{
    "_id": "65c1a2b3c4d5e6f7a8b9c0d1",
    "geo": "FR",
    "name": "От мёртвого осла уши",
    "category_id": 3434222,
    "unit_price": 123.99,
    "quantity": 19,
    "color": "FF0B0C",
    "size": "XXL"
}
```

#### Основные операции

* Частые обновления остатков при покупках.
* Поиск товаров по категориям и фильтрация по диапазону цен.
* Описание товара на странице продукта.

### Carts (корзины)

Коллекция carts хранит данные о текущих корзинах (как гостевых, так и пользовательских) и включает атрибуты:

* Уникальный идентификатор корзины (_id);
* Идентификатор пользователя user_id для залогиненных
* Идентификатор сессии session_id для гостей
* Список товаров (items): массив документов { product_id, quantity }
* Статус корзины (status): "active" | "ordered" | "abandoned"
* Дату и время создания (created_at)
* Дату и время последнего обновления (updated_at)
* Время удаления (TTL) (expires_at) — для автоматической очистки старых корзин

В корзину добавлена геозона для обеспечение локальности данных, см. также секцию Стратегии и ключи шардирования.

Операции с корзиной не резервируют остатки.

```
{
    "_id:" 6a7887ca2530ce7fe34f2af0,
    "user_id": 23234888,
    "session_id": "019fe6d3-ee9b-7ec0-8d6b-0c59293c111f",
    "owner_id": "user:23234888",
    "geo": "FR",
    "items": {
        {
            "product_id": 122122,
            "quantity": 1 
        },
        {
            "product_id": 322323,
            "quantity": 1 
        },
    },
    "status": "active",
    "created_at": "2026-07-15 15:34:22",
    "updated_at": "2026-07-15 15:38:40",
    "expires_at": "2026-07-15 16:38:40"
}
```

Заведено поле owner_id, которое является универсальным идентификатором владельца корзины и по которому можно шардировать.

Корзина локальна для локации (есть соответствующее поле), при перемещении между локациями не выживает (редкое событие).

Заказанные корзины надо как-то очищать в фоне.

#### Основные операции

* Создание корзины, когда заходит гость или новый пользователь.
* Получение текущей корзины по фильтру { session_id, status:"active" } или { user_id, status:"active" }.
* Добавление или замена товара в корзине.
* Удаление товара из корзины.
* Слияние гостевой корзины в пользовательскую, если пользователь залогинится:
    1. прочитать гостевую { session_id, status:"active" };
    1. добавить её items в корзину { user_id, status:"active" };
    1. отметить гостевую как abandoned.
* Отметка корзины как заказанной.

### Стратегии и ключи шардирования

Стратегия строится из следующих предположений:

* Можно определить локацию пользователя, она влияет на то, где резервируются остатки
* Пользователь очень редко меняет локацию
* Если в конкретной локации нет товара, то покупка невозможна (товар не переезжает между локациями)

Архитектурные принципы:

* Есть N датацентров, к каждому приписано несколько локаций со своими остатками
* Все операции стараемся делать ближе к пользователю
* Стараемся избегать транзакций (запросов) между датацентрами
* Транзакций между шардами НЕ избегаем (то есть будет 2PC между шардами, но не между датацентрами, SAGA нет тк нам в некотором роде навязана структура данных)

|**Сущность**|**Ключ шардирования**|**Операция**|**Мотивация**|
| :-: | :- | :- | :- |
| Заказ | ```{ "geo": 1, "user_id": "hashed" }```<br><br>**geo** - геошардинг ```sh.updateZoneKeyRange("playground.orders", { "geo": "FR", "user_id": MinKey }, { "geo": "FS", "user_id": MinKey }, "NL-Zone")```<br>**user_id** - хешированное шардирование | Быстрое создание заказов с одновременным списанием остатков | <ul><li>Заказ всегда создаётся в геозоне, где находится пользователь</li><li>Каждый датацентр содержит свою копию коллекции товаров с локальными остатками</li><li>Создание и списание происходят в одной транзакции, затронет разные шарды, но в одном датацентре</li></ul><ul> |
| | | Поиск истории заказов конкретного пользователя | <ul><li>Пользуемся фактом, что пользователь практически не меняет геозону - тогда запрос по geo пользователя + user_id попадёт в ближайший датацентр и в нужный шард (Targeted Query)</li><li>Для случая миграции пользователей между локациями видимо надо будет как-то запоминать список его локаций и делать несколько запросов - предполагается, что таких пользователей будет мало, также можно попробовать завести реплики заказов из других локаций и форсировать чтение из локальной реплики (см. соответствующую секцию)</li></ul> |
| | | Отображение статуса заказа | Здесь просто точечно ищем по geo + user_id + _id - запрос попадёт в ближайший датацентр и будет запроошен один шард (Targeted Query) |
| Товар | ```{ "geo": 1, "category_id": 1 }```<br><br>**geo** - геошардинг, **category_id** - range-based ```sh.updateZoneKeyRange("playground.products", { "geo": "FR", "category_id": 0 }, { "geo": "FR", "category_id": 2 }, "NL-Zone")``` и ```sh.updateZoneKeyRange("playground.products", { "geo": "FR", "category_id": 2 }, { "geo": "FS", "category_id": 0 }, "NL-Zone")``` - в каждой геозоне своя копия коллекции со своими остатками, по категориям распределяем по шардам внутри зоны, благодаря range-based шардировнию можно вручную устранять перекосы (назначать категории на шарды), это сделано намеренно, тк можно управлять шардированием вручную, категорий не так много, альтернатива - доверить это Mongo | Частые обновления остатков при покупках | <ul><li>Заказ всегда создаётся в геозоне, где находится пользователь</li><li>Каждый датацентр содержит свою копию коллекции товаров с локальными остатками</li><li>Создание и списание происходят в одной транзакции, затронет разные шарды, но в одном датацентре</li></ul><ul> |
| | | Поиск товаров по категориям и фильтрация по диапазону цен | <ul><li>Ищем по geo + category_id - благодаря тому, что в каждом датацентре живёт своя копия у нас будет запрос в один шард (Targeted Query)</li><li>Шардирование по цене видимо можно попытаться применить когда разрастётся одна категория, на начальном этапе подойдёт обычный индекс</li></ul> |
| | | Описание товара на странице продукта | Ищем по geo + category_id + _id - гео берём текущее и пользуемся фактом, что у нас на все локации своя копия, для категорий выглядит так, что для всех use case нам известна категория товара - мы либо попали на товар с поиска по категории, либо например из заказа, но там можно сохранить категорию рядом с товаром - будет также запрос в одну локацию и шард (Targeted Query) |
| Корзина | ```{ "geo": 1, "owner_id": "hashed" }```<br><br>**geo** - геошардинг ```sh.updateZoneKeyRange("playground.orders", { "geo": "FR", "user_id": MinKey }, { "geo": "FS", "user_id": MinKey }, "NL-Zone")```<br>**owner_id** - хешированное шардирование по синтетическому полю, которое содержит или user_id или session_id | Создание корзины, когда заходит гость или новый пользователь | Проискодит по geo + owner_id, попадает в некоторый шард |
| | | Получение текущей корзины по фильтру { session_id, status:"active" } или { user_id, status:"active" } | Используется owner_id, по которому происходит шардирование (,будет Targeted Query в один шард в одной локации), по статусу просто индекс |
| | | Добавление или замена товара в корзине | Эквивалентно кейсу выше |
| | | Удаление товара из корзины | Эквивалентно кейсу выше |
| | | Отметка корзины как заказанной | Эквивалентно кейсу выше |
| | | Слияние гостевой корзины в пользовательскую, если пользователь залогинится | Никаких специальных оптимизаций кроме локальности по гео, считаем кейс редким |

### Примеры настройки кластера

Ниже даны команды настройки модельного кластера.

Кластер расположен в двух датацентрах - RU и NL, в каждом по два сервера - RU: shard-RU-1, shard-RU-2, NL: shard-NL-1, shard-NL-2.

Каждый датацентр обслуживает свой набор локаций - локации DE и FR обслуживаются датацентром NL, локация RU - датацентром RU.

Ниже даны команды настройки двух коллекций - orders и products.

Имя БД - playground.

Docker Compose конфигурация кластера живёт в каталоге 7-playground .

Переходим в каталог:

```
cd 7-playground
```

Запускаем модельный кластер:

```
docker compose up -d --wait
```

Заходим на mongo router:

```
docker compose exec -it mongos_router mongosh
```

Шардируем коллекции orders и products так, как описано выше:

```
(function() {

sh.addShardToZone("shard-NL-1", "NL-Zone");
sh.addShardToZone("shard-NL-2", "NL-Zone");
sh.addShardToZone("shard-RU-1", "RU-Zone");
sh.addShardToZone("shard-RU-2", "RU-Zone");

sh.addShardToZone("shard-NL-1", "NL-Zone-1");
```

## Задание 10: Миграция на Cassandra: модель данных, стратегии репликации и шардирования

Во время «чёрной пятницы» интернет-магазин использовал MongoDB с шардированием на основе диапазонов (Range-Based Sharding). При резком увеличении нагрузки (50 000 запросов/сек.) возникла высокая задержка при масштабировании.

При добавлении новых шардов MongoDB полностью перераспределяла данные между всеми узлами, что вызывало просадку latency в пик нагрузки, так как система тратила ресурсы на перемещение данных.

### Задание 10.1

Допустим запросы и конверсия такие: поиск -( 20% )-> корзина -( 33% )-> заказ

Получится: 39000 поисков, 7800 добавлений в корзину, 2600 заказов в секунду.

Write нагрузка не выглядит достаточной для обоснования Cassandra.

Возможно 50000 rps имелась в виду нагрузка только на запись, тогда будет 37500 добавлений в корзину, 12500 заказов - тоже такое себе.

Не очень понятно, какую сущность шардировали Range-Based - она должна быстро записываться, чтобы вызвать проблемы с перебалансировкой - это или заказы или корзины. Предположим шардировали Range-Based заказы или корзины по id. Это само по себе выглядит ошибкой, выглядит так, что тут просто не нужно использовать Range-Based шардирование.

Тем не менее раз задача про Cassandra, попытаюсь перечислить use cases по убыванию степени выигрыша от Cassandra.

Предполагается, что точно так же существует N датацентров, каждый из которых обслуживает набор локаций.

1. Корзина - самая высокая скорость на запись, целостность не так важна, для консистентности можно сделать LOCAL_QUORUM или вообще не реплицировать корзины в другие датацентры (по всей видимости этого можно достичь только отдельными keyspace).
2. История заказов - скорость на запись умеренная, историю можно записывать отдельно от самих заказов, целостность не так важна, для консистентности можно сделать LOCAL_QUORUM, можно использовать для просмотра заказа уже после того, как он прошёл транзакционный flow.
3. Каталог товаров - для поисков целостность тоже не так важна, видимо можно отделить каталог от остатков товаров - он будет как поисковый индекс, нагрузка будет только на чтение, но на него придётся львиная доля запросов тк это начало воронки продаж, для консистентности можно сделать LOCAL_QUORUM или даже LOCAL_ONE, также можно использовать для просмотра карточки товара.

Что я не стал бы переносить в Cassandra.

1. Заказы + остатки товаров - тут как видится больше подойдёт RDBMS (или та же Mongo, если там относительно честный ACID), типичные проблемы решаются не выбором БД, а архитектурой - reservation pattern, buckets для hot key и тп.
2. Сессии - видимо лучше хранить в чём-то типа Redis, тк их нет смысла реплицировать между датацентрами.
